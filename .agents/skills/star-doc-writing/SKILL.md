# star-doc 技术文档写作规范

用于维护 `star-doc` 的 Markdown 技术文章。目标不是写“看起来很长”的文章，而是让文章更准确、更容易复习、更能解释清楚原理。

## 开始前

1. 先阅读目标文章全文；新增文章时，先阅读同目录至少 2 篇文章，确认标题、段落、代码块、callout 和图片引用风格。
2. 明确文章类型：概念机制、流程图解、API/语法、工程实践、安装备忘录。不同类型使用不同结构。
3. 对不确定的技术事实，优先核验当前项目已有文章、官方文档或规范资料；不能核验时，不写确定语气。

## 推荐结构

### 概念机制类

适用于事件循环、缓存、Fiber、原型链、TCP 流程等内容。

```md
# 主题

用 1-2 段说明这个主题解决什么问题，以及为什么需要理解它。

## 基本概念
解释核心名词和边界。

## 工作流程
按真实执行顺序描述机制。

## 示例
用最小示例验证前文规则。

## 常见误区
说明容易混淆或容易错用的点。

## 实践意义
说明对开发、调试、性能或排障的价值。
```

### API/语法类

适用于 `Promise`、`async/await`、`IntersectionObserver`、模块化等内容。

- 先说明出现背景和要解决的问题。
- 再说明核心语法或 API 形态。
- 然后给出最小可运行示例。
- 最后补充边界、兼容性或常见误区。

### 工程实践/备忘录类

适用于 Docker、SSH、Ubuntu 安装等内容。

- 先说明适用环境和目标。
- 步骤要可执行，命令块使用 `bash`。
- 对可能有破坏性的命令必须写清影响。
- 写明验证方式，例如如何确认配置生效。

## 表达规则

- 中文为主，术语可保留英文；首次出现的缩写尽量补充含义。
- 一段只表达一个重点，长段落拆成短段落。
- 避免“众所周知”“显然”“很简单”等空泛表达。
- 不把推测写成事实。比如浏览器内部实现、规范行为、Node 与浏览器差异必须区分清楚。
- 解释机制时优先写清“谁在什么时候做了什么”，避免只写名词列表。

## Markdown 与 VitePress 规则

- 每篇文章只有一个一级标题。
- 标题层级不能跳级，例如 `##` 下一级是 `###`。
- 代码块必须写语言标识：`js`、`ts`、`bash`、`http`、`text` 等。
- 图片使用 `![说明](/images/xxx.png)`，alt 文本要能说明图片内容。
- 使用 callout 强调补充信息：
  - `[!NOTE]`：补充说明。
  - `[!TIP]`：实践建议。
  - `[!WARNING]`：风险、误区或破坏性操作。
- 站内相对链接优先使用当前已有写法，例如 `./jsExecutionFlow#call-stack`。

## 修改既有文章

- 保留原文中仍然正确的细节，不为了统一风格删除有效解释。
- 修正错误时，应让上下文一起成立，避免只替换单句导致前后矛盾。
- 扩写时优先补齐缺失链路：定义、前提、执行顺序、边界、示例、实践意义。
- 如果文章已有图片或流程图，新增解释应和图片一致；图片过时时先向用户确认是否替换。

## 交付前自查

- 标题是否准确覆盖文章主题。
- 读者能否从前文推出后文结论。
- 示例输出是否和代码一致。
- 是否混淆浏览器、Node.js、ECMAScript 规范、HTTP 标准或具体实现。
- 是否需要同步 sidebar/nav；需要时继续使用 `/star-doc-navigation`。
